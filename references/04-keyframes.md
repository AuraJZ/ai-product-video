# 04 关键帧：把底图画成照片

关键帧是每个镜头的首帧、尾帧（长镜头还有中间帧）。**写实感全部在这一步产生**，视频模型只负责"变化"。

## 1. 关键帧在流水线里的位置

- **关键帧要直接驱动镜头**：当首帧、尾帧或有序关键帧用。不要把它当成五张参考图里的一张，更不要配一句"不要用这张图的机位"。视频模型跟着最强的信号走，弱参考几乎不起作用。
- **在锁定的底图上重画**：底图永远是上传的"图1"，图像模型只把灰模画成真实拍摄的样子，不改构图（底图见 03）。没有 3D 时，"图1"是 2D 合成底图或实拍代理照片。
- 写实感必须已经在关键帧里。如果关键帧本身就假，视频不会让它变真。

> 案例：某产品片一开始只把图像模型画的场景图当成五张参考图之一，产品特写全是 3D 渲染。用户看完问"我让你生成的那些图，在视频里根本没用上"。改成"每张关键帧都在底图上重画、直接当首尾帧"之后，质感才过关。

## 2. 统一设定（look bible）

图像模型的每个新对话互不记忆。**一致性只能靠文字**：所有关键帧的提示词都以同一段"统一设定"开头，一字不改。

原则：

1. **逐字节相同**。用脚本核对每份提示词开头的统一设定段落哈希值一致。改一个字，就重新生成所有还没画的出图包。
2. **只写全片不变的东西**：画面质感、"图1决定构图"这条规则、每个产品的外观、连接件、场景、人物规则、文字规则、画幅。
3. **例外单独写一行**，标明"本张例外（改写统一设定第 N 条）"，写清为什么、具体改成什么。不写明例外，全局规则会悄悄盖掉这张图的意图。
4. **一种语言写到底**。中文或英文都可以，有的图像模型对英文更敏感，先用两三张测试再定，定了就不要中途换。

统一设定通常 9 条：

| # | 内容 | 为什么这么写 |
|---|---|---|
| 1 | 画面质感：像用电影摄影机和定焦镜头实拍的〈品类〉广告剧照；透视、焦段、景深以图1为准；高光、暗部、色彩、颗粒、材质 | 把风格锁在"实拍"，排除 CG、塑料、插画感 |
| 2 | 图1是布景底图：构图、机位、每样东西的位置、轮廓、比例、连接线走向都和图1一致；其他图只参考长相 | 把"构图由底图决定"说死 |
| 3–5 | 每个产品、连接件的外观：尺寸、形状、颜色、材质、字样、接口位置；"只反射环境光，本身不发光" | "不发光"专门压住模型把材质颜色画成灯的毛病 |
| 6 | 场景：家具、墙地面、窗、灯逐项写；"只画图1里看得到的部分" | 防止模型按描述往画面里加东西 |
| 7 | 人物：不出现人脸 | 见第 9 节 |
| 8 | 文字：除产品本身的字样外，没有任何文字、标志、水印 | 模型爱加假字 |
| 9 | 画幅：横版 16:9 或竖版 9:16，一张完整的照片，不拼图，不留白边 | 防止输出拼图或留边 |

**解说片和广告片的差别**：解说片的第 1 条通常是中性、克制的家居或影棚质感；广告片可以在第 1 条里写品牌的色调、光线风格和调色方向（比如"暖色、逆光、浅景深"），但同样要全片一致。

完整的可填模板见 `templates/prompts/look_bible.md`。填好的统一设定存成项目的 **`packs/look_bible.txt`**，这是它唯一的来源：出图包、API 脚本都从这个文件原样拼接，哈希核对也以它为准。

## 3. 关键帧清单

用一个数据文件 `keyframes/keyframes.json`（模板 `templates/keyframes.example.json`）列出所有要画的图，项目自己的脚本据此生成出图包（`packs/`）和检查任务：

```json
{"id": "S05-K00", "shot": "S05", "t": 0.0, "role": "first",
 "purpose": "Product on the desk, indicator off, before the user touches it",
 "person": "none", "fx": {"indicator_on": false},
 "uploads": ["plates/S05-K00/plate.png", "keyframes/norm/M1.png", "keyframes/norm/R1.png"],
 "save_as": "keyframes/raw/S05-K00.png", "depends_on": []}
```

- `id` 的写法：`<镜头>-K<秒数>`，K00 是第 0 秒，K04 是第 4 秒，K035 是第 3.5 秒。秒数按**生成片段**的时钟（镜头表的 `gen_duration`），不按剪辑后的长度：成片里 3 秒、生成 4 秒的镜头，尾帧是 K04。
- `role`：`master`（母版）、`first`、`mid`、`last`。
- **母版先画，先过检查点**：第一轮只画母版，每张画完都停下来给用户看，认可后才出镜头关键帧的出图包。母版有三类：
  - 产品母版：每件产品一张，中性灰底，做后面所有图的外观参考；
  - 场景母版：片中用到的每个地点、每个时段各一张；
  - 人物设定图：片中有人物时一张，身份来源按第 9 节的人脸政策定（多数视频平台只认它信任的来源）。
  之后每张关键帧都把相关母版当图2、图3……上传。母版认可之后再改，用它画过的关键帧都要重新检查。
- 然后按镜头顺序画。
- `depends_on` 写明依赖：同一镜头的尾帧要上传已画好的首帧。

## 4. 单张出图包

每张关键帧一个文件夹，外加一份把整轮串起来的说明文件（比如 `本轮出图_8张.md`）。模板见 `templates/prompts/keyframe_pack.md`。

每张图写这几项：

| 项 | 内容 |
|---|---|
| 用途 | 一句话：这张图在片里做什么 |
| 按顺序上传 | 图1 永远是底图；然后是产品母版、场景母版、同镜头已画好的前一帧。文件按 `01_`、`02_` 编号，用户按编号拖进去 |
| 提示词 | 统一设定 + 本张补充，放在**同一个**代码块里，**整段复制、作为一条消息发出**；块外不放任何要粘贴的文字，`prompt.txt` 和代码块逐字相同 |
| 存成 | 精确的文件名和文件夹 |
| 画完检查 | 3–5 条，用户自己能看出来的标准 |
| 不合格时 | 一句**固定的**纠正话，只用一次 |

本张补充的写法（每段一行）：

```text
本张例外（只对这一张，改写统一设定第〈N〉条）：〈为什么例外，具体改成什么〉
本张上传：图1 = 〈是什么，照它的什么〉；图2 = 〈是什么，照它的什么、不照它的什么〉；……
本张画面：〈时间、景别、主体、背景〉
光线：〈光从哪来、多强、什么颜色、哪里暗〉
效果状态：〈这一刻效果处在什么状态，按摄影机看得到的样子写；它不是什么〉
人物：〈没有人 / 只露背影或后脑 / 头在画外〉
特别注意：〈最容易画错的 1–2 点〉
```

流程规则：

- **每张图都在图像模型里新开一个对话**。
- 不合格时只回复一次固定纠正话，还不行就**新开对话重画**。不要在同一个对话里反复改，每改一次都会再走样一点。纠正话按路线二选一：
  - 有 3D 底图："构图、产品位置和大小必须和图1完全一致，只把灰模画成真实照片；其他要求不变，请重画一张。"
  - 无 3D 路线（图1 是 2D 合成底图或实拍代理照片，统一设定第 2 条用无 3D 写法）："构图、机位和产品的位置大小必须和图1完全一致，图1里代理物的位置就是产品；产品外观照图2。其他要求不变，请重画一张。"
- 下载原图（不是截图），按"存成"的名字放好。

**补拍镜头：没有底图时**

后期补的镜头常常没有 3D 底图。做法：

1. 图1 改用同一场景里一张**已经批准的关键帧**（构图最接近的那张），其余照常上传母版；
2. 在本张补充里写"本张例外（改写统一设定第 2 条）：这张没有布景底图，图1 是已批准的关键帧〈id〉……"，写清照它的什么、只改什么（写法见 `templates/prompts/look_bible.md` 和 `keyframe_pack.md`）；
3. 这张图没有底图契约（遮罩、坐标），Gate K 改为和图1 比对产品轮廓、比例和效果状态，再加一遍人工检查，结果照样写进报告；
4. 镜头表里这张关键帧的 `source` 写 `image_from_keyframe`；提交视频照常用首尾帧模式，不依赖底图。

## 5. 检查点与节奏

- **第 0 轮是母版**（第 3 节）：每张母版都是检查点，用户认可后才进入镜头关键帧。
- 每一轮的前 2–3 张设检查点：画完先停下，发给 AI 助手检查，通过再画后面的，避免整批返工。新场景、新效果的第一张也设检查点。
- 手工画一张大约 5–7 分钟。一次坐下来画 8–10 张比较合适。
- 把手工出图安排在"等待"的时间里：账号额度冷却、长渲染、模型排队。
- **轮到用户动手时，在同一轮回复里就把完整的说明文件交出去**，不要只发一句"可以开始画了"。

## 6. 统一到输出尺寸

图像模型返回的尺寸常常不是精确的 16:9（比如 1672×941），格式也不一定是 PNG。送进视频模型之前统一处理：

1. 镜头帧（首帧、中间帧、尾帧）先居中裁成精确的目标比例（16:9 或 9:16），再缩放到输出分辨率（比如 1080×1920），**不超过输出分辨率**——过高分辨率的参考图可能在视频里产生类似"指纹"的细纹；
2. **母版和参考图不裁**：横版的产品参考表裁成竖条就只剩一截，只按自己的方向缩小；
3. 源图比输出小时会被放大，要看到警告：放大的帧发软，能重画大一点就重画；
4. 同一镜头的首尾帧尺寸完全相同；
5. 存到 `keyframes/norm/`，**只有这里的文件会送进视频模型**，原图留在 `keyframes/raw/` 不动。

用附带脚本（读 `keyframes/keyframes.json` 里的 role；没有清单时，M、R 开头加数字的 id 当母版和参考图）：

```bash
uv run scripts/qc/normalise_keyframes.py --project <project> --size 1080x1920 --dry   # report only
uv run scripts/qc/normalise_keyframes.py --project <project> --size 1080x1920
```

它读 .png .jpg .jpeg .webp，写 `<id>.png`；放大（UPSCALED）、比例差太多被硬裁（CROPPED，多半是画错了方向）、同一个 id 有两种格式（DUPLICATE）都会警告。说明见 `scripts/qc/README.md`。

## 7. Gate K：花钱之前的关键帧检查

Gate（闸门）是一个自动检查：检查不过，就不花视频生成的钱。Gate K 把每张归一化后的关键帧和它的底图比对。

**它是项目自己的脚本**（放在 `work/`，例如 `work/gate_k.py`），本 skill 不附带现成的：遮罩、底图、产品和效果都因项目而异。下面写的是它要测什么、怎么校准、怎么放行。附带的 `scripts/video_api/seedance.py` **不读** Gate K 报告；"没有报告或报告是 FAIL 就不提交"由项目自己的提交步骤保证：一个包装脚本在调用 `seedance.py submit` 之前查 `qc/` 里这张图的报告和 sha256，或者一张提交前逐项打勾的清单。

### 7.1 自动检查项

| 检查 | 怎么测 | 抓什么 |
|---|---|---|
| 轮廓 | 用遮罩边缘和画作的边缘做匹配，和底图自己的得分比 | 产品变形、多了少了部件 |
| 长宽比 | 拟合产品轮廓，比较宽高比 | 产品被压扁或拉长 |
| 位置与缩放 | 在产品区域估算平移和缩放 | 构图漂移。经验阈值：缩放超过 6% 或平移超过画宽 3% 判失败 |
| 同镜头一致性 | 同一镜头几张关键帧之间的缩放和位置差 | 差太多，到视频里就成了没设计过的推拉。经验阈值：缩放差超过 4% 要复核 |
| 效果状态 | 对比 `plate` 和 `plate_fxoff`，看画作的指示灯区域在"开"还是"关"，色相是否接近底图 | 模型自作主张开灯、关灯、改颜色（比如琥珀色变粉色） |
| 光晕 | 产品轮廓外一圈的亮度台阶 | 产品边缘被画成灯带 |
| 连接件 | 沿 `cable_polyline_px` 取样，看线还在不在 | 线缆消失、改道 |
| 产品数量 | 连通区域计数 | 画出两个产品 |
| 重复文件 | 缩略图差异或文件哈希 | 同一张图存成了两个名字 |

### 7.2 风格检查（人眼，列在报告里）

- 有没有 CG 感、塑料感、过度锐化、HDR 光晕、过饱和；
- 有没有多出来的文字、假字样、镜像字、水印；
- 有没有人脸、眼睛、鼻子、嘴；
- 材质有没有"自己发光"；
- 有没有凭空多出来的接口、按钮、物体；
- 和同镜头其他帧、和场景母版的色调是否一致。

### 7.3 校准与放行

- **先校准再信它**。用两类样本：已知好的（底图本身当作画作输入，必须通过）和人为制造的坏样本（关灯、改成粉色、平移 3%、放大 5%、压扁 10%、擦掉线缆、加光晕），确认坏样本都被抓住。阈值以"底图自己的测量值"为基准，而不是写死的颜色数值。
- 结果分三档：PASS / REVIEW（待人工复核）/ FAIL。
- 自动判 FAIL、人眼确认没问题时，写**人工放行记录**：理由、谁看的、时间，并**绑定这张图的 sha256 文件指纹**。图一改，放行自动失效。
- 不要靠放宽阈值了事，也不要绕过闸门提交。
- 每张图出一张对照图（底图和画作并排，叠加轮廓线），给人眼看。

> 案例：某产品片第一次在真实画作上跑 Gate K，42 张里 5 张通过、31 张待复核、6 张失败。逐张目测后，合理的重新诠释（比如替身被画成盖着被子的人）写进放行记录；真正的问题（灯被画亮、同一镜头缩放 +9% 和 −8%）退回或救图。

## 8. 画偏了先救：配准

很多"失败"只是缩放或平移偏了，不必重画：

1. 用图像配准（比如 OpenCV 的 ECC 算法，相似变换：缩放 + 平移，必要时加小角度旋转），在产品遮罩区域把画作对齐到底图；
2. 按算出的变换把整张画作变换回底图的画框；
3. 补齐露出来的边：轻微放大裁切，或用图像模型补边；
4. 重新跑 Gate K，并把变换参数写进报告。

> 案例：某产品片的一张尾帧，产品被画大了约 12.6%。配准（缩放系数约 1.12）后通过检查，省掉一轮重画。

另外两种"救法"：

- **改剧本迁就画面**：画师的改动更自然、更安全时（比如人物被画成背对镜头侧躺，正好藏住脸），保留画作，改视频提示词的结尾去配合它。
- **换生成模式**：发现首帧和尾帧其实是同一张图，可以改用"只给首帧"的模式，不必重画。

## 9. 人脸政策

先查清视频模型对人脸的限制，**再设计关键帧**。很多视频模型拒收写实人脸的参考图，图像模型画出来的写实脸也会被拒。

默认做法：

- **所有关键帧都不画脸**：背影、过肩、侧后方、头在画外、只出现手；
- 底图里的替身头转开（见 03），统一设定第 7 条写"不能有眼睛、鼻子或嘴"；
- 检查时逐张看有没有脸。

必须露脸时：

- 人物身份只用平台认可的"可信来源"（比如同一平台、同一账号的图像模型生成的原始文件），**原始文件、原始链接，不裁剪、不重新编码**，否则失去"可信"身份；
- 露脸的那几秒不给关键帧，由视频模型按人物设定图生成；
- AI 过渡镜头（见 05）只用在画面里没有脸的接口；
- 绝不使用真人照片做人脸参考，除非有本人书面授权并符合平台的肖像规则；不使用公众人物（见 `09-compliance.md` 第 6 节）。广告片需要真人演员时，考虑实拍或有授权的数字人。

## 10. 两种出图方式：人在订阅里画 / 脚本调 API

**先问用户手上有哪种工具，不要默认手画。** 只有会员订阅、没有 API 的，走 A；有 API（或愿意开通）的，可以走 B 或混合。问法见 `01-intake.md` 第 11 节第 17 问。

| | A. 用户在自己的订阅里画 | B. 脚本调 API |
|---|---|---|
| 适合 | 用户有图像模型的会员订阅、没有 API；主镜头、要求最高的画面 | 数量多、要可复现；母版、简单镜头、批量重画 |
| AI 助手做什么 | 生成出图包和说明文件；检查；归一化；Gate K | 写提交脚本；dry run；提交；记录；检查 |
| 用户做什么 | 新开对话、上传、粘贴、下载、存档；每张约 5–7 分钟 | 把 API Key 放进本地 `.env`；批准预算 |
| 优点 | 通常能用到最新的模型和界面功能；用户自己把关审美；不需要密钥 | 快、能批量、有日志、能算成本 |
| 缺点 | 慢、靠手工；不同会话之间难完全一致 | 按张计费；API 版本和网页版效果可能不同 |
| 注意 | **商用条款**：消费级订阅的条款不一定允许广告用途，投放类广告优先走企业 API 或确认条款 | 密钥只放 `.env`，AI 助手只检查变量是否存在，不读、不显示内容 |

混合做法：母版和简单镜头用 API，主镜头由用户手画。两种方式产出的图都要过同一个 Gate K。

视频模型同样分两种入口，要单独问（`01-intake.md` 第 11 节第 18 问）：API 账号可以用附带的视频脚本；只有网页或 App 会员时，视频也由用户手动生成，用 `templates/prompts/video_pack_manual.md` 的手动视频包，并先核对会员条款和有没有草稿升级（`05-video-gen.md` 第 14 节）。

## 11. 工具备注（2026-10，使用前核对最新文档）

方法和模型无关。下面是当时用过或常见的选择，能力变化很快，换模型前先用 2–3 张底图做对比测试：

- **ChatGPT（GPT Image）**：支持一次上传多张图并按顺序引用；能较好地保留物体轮廓，但会悄悄改画幅、缩放（实测同一镜头 ±10% 左右）和效果状态（灯的开关），所以 Gate K 和配准是必需的。网页版返回的尺寸不一定是精确 16:9。
- **Seedream（字节跳动）**：有 API，适合批量；当时它生成的人物原图是同一平台视频模型（Seedance）唯一信任的人脸来源。
- **Nano Banana（Google Gemini 的图像模型）**：擅长"按参考图编辑并保留布局"，值得作为底图重画的候选来测试。
- **Midjourney**：氛围和质感强，但对给定构图的服从度一般，更适合做质感参考，不适合在底图上精确重画。
- **Flux（含 Kontext 编辑版）**：可以本地或通过 API 运行，适合带参考图的编辑；同样要先测构图服从度。
