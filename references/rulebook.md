# 规则手册：AI 产品视频（讲解片与广告）

适用于任何实体产品的**讲解片**（功能演示、投资人路演、发布会短片）和**广告**（信息流、贴片、社媒短视频、电视）。默认流程是：3D 预演定位 → 图像模型在底图上画写实关键帧 → 视频模型生成镜头 → 用代码剪辑，字幕、标注和声音都按时间线数据生成。不做 3D 的项目跳过第 2 组，用实物照片或官方渲染图当"产品真相"，其余规则照用。

**怎么读**

- 每条规则：加粗的一行是做法；"为什么"一句；"案例"或"来源"一句。
- 标签：〔广告〕只对广告成立；〔讲解片〕只对讲解片成立；没有标签的两种都适用。
- "案例"都来自同一支实际完成的 AI 产品片（2026-10，某智能硬件产品的投资人讲解片，约 2 分钟，中英双版），产品细节已隐去。
- "来源：通用实践"表示广告行业的常规做法，案例项目没有覆盖；用之前按你的投放平台和当地法规核对。
- 出了问题先查 `pitfalls.md`（现象 → 先查什么 → 对应规则）。

## 先认这几个词

| 词 | 意思 |
|---|---|
| 讲解片 | 讲清"产品是什么、怎么工作"的片子：功能演示、投资人路演、发布会短片，通常 1–3 分钟 |
| 广告 | 为了让人记住或购买而投放的片子：信息流、贴片、社媒、电视，通常 6–60 秒，公开播放 |
| 产品方 | 对产品事实负责的人：创始人、产品经理或客户 |
| 底图（plate） | 3D 软件按真实机位渲染的定位图，图像模型在它上面重画成写实关键帧 |
| 灰模视频（clay video） | 3D 软件渲染的纯灰色预演视频，只告诉视频模型机位、走位和时间，不提供长相 |
| 替身（stand-in） | 预演里代替真人的灰色简易人形 |
| 首尾帧模式 | 视频模型的一种生成方式：给开头和结尾两张图，让模型补中间 |
| 多参考模式 | 另一种生成方式：给多张参考图加一段参考视频，让模型综合；各家模型叫法不同 |
| 草稿升级 | 先出便宜的低清草稿，批准后把同一个任务原样升到高清，不重新生成 |
| 闸门（gate） | 自动检查，检查不过就不花钱；Gate K、Gate V 的判定是项目自己写的脚本，附带的视频客户端只检查请求本身 |
| EDL | 剪辑决定表：一个数据文件写明每个镜头用哪一段、多快、怎么转场、配哪条字幕，剪辑程序照着出片 |
| 词表闸门 | 检查上屏文字和配音稿里有没有规格数字、功效、医疗、绝对化用词的脚本 |
| 闪避（ducking） | 某个声音出现时，把音乐自动压低几 dB |
| LUFS / dBTP | 响度单位 / 真峰值单位，网络视频常用 −14 到 −16 LUFS |
| 钩子（hook） | 广告开头 2–3 秒里让人停下来的画面或一句话 |
| CTA / 片尾卡 | CTA 是行动号召（去哪买、搜什么、扫码）；片尾卡是片尾停住的品牌画面 |
| 剪短版（cut-down） | 从同一支主片剪出的 30 / 15 / 6 秒版本 |
| 安全区 | 画面里不会被平台按钮、文案或屏幕边框挡住的区域 |
| brief / agent | brief 是交给子任务的说明文件；agent 是 Claude 派出去并行干活的子助手 |

## 最重要的 12 条

1. **开工先写立项单：讲解片还是广告、给谁看、在哪播、多长、什么画幅**（→0.1）。这几项决定节奏、画幅、合规尺度和成本。
2. **产品事实和工作原理先写成文件，请产品方确认后再建模；事实一更正，一次改完所有下游，再全局搜残留词**（→0.2、0.3、0.4）。错一个事实，后面全部返工。
3. **3D 只负责定位，最终像素交给 AI 画**（→2.1）。每个镜头都问一句"最终像素从哪来"。
4. **AI 关键帧要当首帧或尾帧来驱动镜头，不能只做参考之一**（→3.1）。
5. **喂给视频模型的每个像素都会被照抄，所以只给它你想让它学的东西**（→2.7、4.3）。
6. **长镜头的提示词写成逐秒剧本，里面的数字由脚本从 3D 场景导出**（→1.5）。
7. **写效果时从真实来源出发，按摄影机拍到的样子写，并写清"不是什么"**（→4.4、4.5）。
8. **花钱分两级：先过免费闸门、出低清草稿，用户批准后才把同一任务升到高清**（→4.8、4.9）。
9. **每条草稿逐帧看，独立审查必须看生成的原片**（→5.2、5.4）。
10. **字幕、标注、logo 和声音都放在剪辑层，按时间线数据生成，改字不用重新生成画面**（→7.1、9.1）。
11. **所有上屏文字和配音稿先过词表闸门，再对照产品事实查"暗示的功能"；广告不造假证言，不展示买到手没有的功能**（→8.1、8.2、8.3、8.7）。
12. **用户的每条反馈按原话编号写进 brief，所有 agent 和终审都对照它**（→5.5）。长会话会被压缩，文件不会。

## 0 立项与事实

操作细节见 `01-intake.md`。

**0.1 开工先写一页立项单：片型（讲解片 / 广告）、目标观众（内部还是公开）、播放场景和平台、时长、画幅、语言版本、要不要配音、交付日期、预算上限，请用户确认。**
- 为什么：这几项决定节奏、画幅、合规尺度和成本，做到一半再改就等于重做；观众是内部还是公开，还决定了能不能拍爆炸图、透视图和内部部件的引线标注（见 8.11）。
- 案例：片子原本只给投资人看，做完后要拿片段发社交平台，才发现透视镜头都不能公开用，只好另挑镜头。

**0.2 建模前和产品方逐项确认外观事实：外形和尺寸参照、正面朝向、接口和出口位置、线缆走向、颜色和材质；每次更正都写进规格文件。**
- 为什么：说明文档和设计图会过时或有歧义，事实错一处，后面的渲染和生成全部白花。
- 案例：第一天就被指出一个出口的位置画反了、主机的尺寸比例也不对，已建好的模型只能停渲重建。

**0.3 把每个功能"靠什么部件、怎样产生、先后顺序如何"写成功能事实文件，放在生成工具之外；自己推断的内容一律标"待确认"。**
- 为什么：图像模型、视频模型和 Claude 都会编出看起来合理、实际不存在的部件。
- 案例：产品方说过内部布局还没定，Claude 就按旧文档推断了一套内部结构，并据此建模、出图、写标注；产品方指出实际机理完全不同，这些全部重做。

**0.4 一处事实被更正，就一次改完所有下游（3D 模型、底图、关键帧数据、画图和视频提示词、标注、字幕、配音稿、brief），再全局搜旧说法的残留词，旧文档标"已被取代"。**
- 为什么：漏改的那一个文件，会在下一次生成时把错误画回来。
- 案例：机理更正后全局搜了旧术语、给旧文档加了"已被取代"标题，复审时仍在一个透视镜头里发现旧机理留下的一缕效果，只好关掉重渲。

**0.5 文档之间冲突时以最新的产品定义为准；产品方的口头说法与文档冲突时以产品方为准；用了哪一份，要告诉用户。**
- 为什么：规格文档总是落后于设计。
- 案例：两份产品文档对同一个部件的位置说法不同，按新版做并明确告知用户；另一处机理以创始人口述为准，覆盖了文档。

**0.6 〔讲解片〕写分镜前把每项功能列成清单，逐项确认片里有对应镜头；做透视图或爆炸图前，先拿到完整的可见部件清单。**
- 为什么：漏掉的功能要在后期补镜头，成本高得多。
- 案例：粗剪后用户指出缺了两项功能的镜头，补了 5 个新镜头；一张透视图在定稿前又补上了 4 个漏标的部件。

**0.7 推荐流程和模型前，用最新、交叉核对过的资料确认各模型的能力、价格、输入限制和商用条款，并在控制台确认真能开通。**
- 为什么：模型版本、价格和政策按月变，记忆里的信息靠不住。
- 案例：调研时推荐的图像模型版本，到控制台一看已"停止新购"，只好临时换成同系列的另一版。

**0.8 承诺排期前，在实际机器上测真实的单帧渲染耗时（不算第一帧的编译时间）；效果定稿后再按实测重估一次。**
- 为什么：体积雾、体积光这类效果会让耗时翻 2–3 倍。
- 案例：纯 3D 方案估计要十几个小时，在没有独立显卡的笔记本上实测要 60–70 小时，于是改成"3D 定位 + AI 出像素"的混合流程。

**0.9 对标片只当质量线：先测量它（运动量、运镜速度、制作方式），列出它的缺点，不照抄它的结构和节奏。**
- 为什么：测量能看出它的真实做法，照抄结构会把缺点一起抄来。
- 案例：拆解对标片发现 13 个镜头里有 9 个几乎不动，本质是"每个镜头一张写实静帧，轻微动起来"，而且它也有人物漂移和乱码字。

**0.10 定路线前，拿同一个镜头花几块钱做对比小测（比如"3D 渲染当首帧"对"AI 写实关键帧当首帧"），看完再定架构。**
- 为什么：几分钟的小测，比整轮做完再推倒便宜得多。
- 案例：第一批草稿里唯一被认可的，恰好是用写实关键帧当首帧的那一条；没有先做对比，白做了一轮。

**0.11 定出图方式前，先问用户手上有哪种图像工具：只有会员订阅（在网页或 App 里手动画），还是有可以由脚本调用的 API；按答案定方式，不默认让用户手画。**
- 为什么：手画每张要占用户 5–7 分钟，API 能批量、可复现、有日志；哪种更合适取决于用户已有什么、预算和对画质的要求。
- 案例：案例项目的用户只有图像工具的订阅、没有 API，所以关键帧全部手画；当时也有可以按张计费、由脚本批量出图的路线，只是没有走。

## 1 创意与脚本

操作细节见 `02-formats.md`。

**1.1 〔讲解片〕先单独介绍每个组件，再介绍它们组合起来的系统。**
- 为什么：观众先认识零件，系统才讲得通。
- 案例：用户要求每个组件先单独亮相，开场因此改成两张组件特写，再接一个系统全景。

**1.2 演示功能时先拍源头、再拍效果（先拍产品上的灯亮起，再拍墙上的光）；同一条顺序规则同时用到所有对称段落。**
- 为什么：先因后果，功能才好懂；只改一边，用户还会再指出另一边。
- 案例：一段的顺序改好后，用户又指出对称的另一段也该先拍产品上的灯、再拍墙面。

**1.3 调整镜头顺序后，逐镜检查时间段和光线状态是否还连贯；不连贯就新生成一个镜头，并重读受影响镜头的关键帧提示词。**
- 为什么：硬塞一个光线不对的旧镜头，故事会穿帮。
- 案例：重排后，一个阳光照着的特写会排到更早的暗场之前，于是新生成了一个暗场版本；同时发现某个表面的颜色会在相邻镜头之间来回跳变，改了提示词。

**1.4 每个效果只展示真正产生它的那个部件，其他部件隐藏或压暗。**
- 为什么：展示错了部件，就等于对观众讲错了产品。
- 案例：一个透视镜头把效果画在了错误的内部部件上，产品方指出起作用的是另一个部件；另一条与事实不符的"内部变化"镜头整条删掉。

**1.5 多秒长镜头写成逐秒剧本：每一秒的机位和速度、画面里什么东西在哪、人物身体怎么动、头发和布料的状态、每个效果的状态、线缆走向；里面的数字由脚本从 3D 场景导出，不手写。**
- 为什么：提示词太短，动作和细节就全靠运气；手写的时间会和参考视频对不上。
- 案例：第一批草稿被用户否掉：「这个提示词要像一个影视剧本那样细化」；同一天手写的效果时间和参考视频差了约 1.5 秒，生成的颜色变化是倒着走的。

**1.6 每张关键帧的描述都要从真实机位做几何投影验证，确认这个画面在该机位下拍得出来。**
- 为什么：脑子里想得通的构图，相机未必拍得到。
- 案例：审查 agent 发现一张"肩和头发在画内、脸在画外"的结尾关键帧，从结尾机位根本拍不出来，剧本和关键帧都改了。

**1.7 动作和运镜都省着用：每 4–5 秒只安排一个动作高峰；每个镜头只用一种慢速、单方向的运镜并写明数字（如推近每秒约 2%，总共不超过 10%）；首帧里没有的东西不要在运动中露出来。**
- 为什么：组合运镜或快速运镜会让画面不稳，首尾帧之间新露出来的东西都是模型编的。
- 案例：对标片显得自然，正是因为动得少；一个环绕运镜让线缆看起来像 V 形折弯，只好改小环绕角度。

**1.8 〔广告〕一支广告只讲一个信息：一句话说得出的卖点，加上一个证明它的画面；其他卖点留给别的片。**
- 为什么：观众只看几秒，塞进三个卖点等于一个都没记住。
- 来源：通用实践。

**1.9 〔广告〕前 2–3 秒必须出现钩子：用产品、问题或反差画面直接开场，不用 logo 淡入或空镜铺垫。**
- 为什么：信息流里观众在头几秒就决定划不划走，可跳过的贴片广告几秒后就能跳过。
- 来源：通用实践。

**1.10 〔广告〕品牌和产品在前几秒内清楚露出一次，结尾再露出一次，不要等到最后才揭晓。**
- 为什么：大多数人看不到结尾，只在结尾出现的品牌等于没出现。
- 来源：通用实践。

**1.11 〔广告〕结尾给一个明确的行动号召（只放一个）和片尾卡：品牌、产品名、一句口号、去哪买或搜什么；片尾卡静止至少 2 秒（6 秒版至少 1 秒），竖屏信息流可以把行动号召交给平台的购物车或链接组件。**
- 为什么：看完想买的人需要知道下一步做什么；行动号召一多就没人照做，片尾卡太短又读不完。
- 来源：通用实践。

**1.12 〔广告〕按无声观看设计：只看画面和上屏文字也能懂，声音只是加分。**
- 为什么：信息流里大量视频默认静音自动播放。
- 来源：通用实践。

**1.13 〔广告〕写脚本时就规划好剪短版：先定主片结构，再标出哪些镜头进 30 / 15 / 6 秒版，确保每个版本都有自己的钩子、卖点画面和片尾卡。**
- 为什么：剪短版只能从主片的镜头里挑，脚本阶段没留好，后面就得补生成。
- 来源：通用实践。

## 2 3D 预演与底图

操作细节见 `03-previs.md`。不做 3D 的项目，把本组里的"3D 模型"换成"实物照片 / 官方渲染图"来读。

**2.1 3D 只锁定构图、机位、走位、产品比例和效果时间；最终像素由图像和视频模型来画，3D 原始像素不进成片（用户明确要 CG 风格时除外）。**
- 为什么：纯 3D 像素一看就是 CG，视频模型又会照抄它看到的画面风格。
- 案例：早期草稿和 3D 低采样预览的相似度高达 0.91–0.98，一股 CG 味；用户指出"3D 是用来固定场景的"，改成 AI 出最终像素后质感才达标。

**2.2 借鉴 AI 漫剧流水线的纪律（先锁资产、先静后动、按镜头选模型、逐镜质检），但把"标准答案"从 AI 关键帧换成 3D 模型加书面产品事实。**
- 为什么：漫剧观众能容忍细节走样，产品片画错一个接口就是在说假话。
- 案例：开工时调研了 AI 漫剧的工业流程，最后整体照搬，只改了"以什么为准"这一处。

**2.3 产品只建一个母版，以链接方式放进每个镜头（不复制），用脚本检查没有镜头私藏副本；所有相关数值都从规格文件计算。**
- 为什么：这样"产品外观一致"由代码保证，改一个尺寸全片自动跟着变。
- 案例：主机尺寸更正时只改了规格文件、重建母版，所有镜头自动更新，一致性检查通过。

**2.4 规格或镜头表一变，立刻停掉正在跑的渲染。**
- 为什么：按旧规格渲出的帧全是浪费。
- 案例：尺寸更正和镜头表改动时，都当场停掉了还在渲旧版本的批次。

**2.5 先用固定的多视角对照图，把产品反复调到和品牌图或实物照一致，交用户确认后再做效果和镜头。**
- 为什么：外观问题在静帧阶段改最便宜，用户通常也想先看。
- 案例：多视角对照图改了四轮，处理了曝光、表面纹理、外壳鼓包和灯的亮斑，确认后才进入镜头制作。

**2.6 生成前从每个真实机位（不只是俯视图）检查 3D 场景：产品朝向、线缆走向、效果从哪出来、有没有穿模；底图先修好再交出去。**
- 为什么：底图是画师眼里的"产品真相"，场景里的错误会传到之后的每一次生成。
- 案例：主机在场景里被转了 90°，正面始终拍不到、插头反而朝着镜头；一根线缆在家具边角像发夹一样扎进布面。

**2.7 送给视频模型的任何像素都会被照抄：灰模视频统一灰色并降噪，底图里的 CG 瑕疵先修掉，效果颜色在静帧和参考视频里都定好。**
- 为什么：参考视频是最强的信号，提示词里写"不要"压不住像素。
- 案例：低采样预览里的噪点被画成了"砂纸"家具和"花岗岩"外壳，粗网格的窗帘变成了锯齿边。

**2.8 预演替身只做"躯干 + 头"，用真实身高，不与道具穿插；身体动作改用文字一步步描述。**
- 为什么：四肢是方块的替身，会教模型做出僵硬、互相穿插的动作。
- 案例：方块替身让人物在 0.17 秒内从站到坐、身体扭转 90°；换成躯干加头，再把"手撑、挪身、抬腿"逐步写进提示词，动作才自然。

**2.9 效果只待在它所属的表面和尺度之内，并且不能和真实机理矛盾：画面里有雾，观众就会认为产品会出雾；有光，就会认为产品有灯。**
- 为什么：越界的效果看起来假，观众还会从画面推断出产品没有的功能。
- 案例：声音的可视化波纹画到了旁边的家具上，另一个效果在产品后面堆成了一堵墙，加了裁切和高度上限才正常。

**2.10 重新渲染前，先确认渲染程序实际从哪个文件读参数；缓存遇到输入变化不能悄悄跳过，要有强制重渲的选项。**
- 为什么：从错误来源渲一张底图要十分钟左右，全部白费。
- 案例：在镜头文件里关掉了一个效果，底图的参数其实取自关键帧数据文件，只好停下重改；另一次渲染脚本直接跳过了"已存在"的旧底图。

**2.11 机器弱时，本地渲染一次只跑一个进程，要有日志、能续跑、失败自动重试；CPU 先让给挡住下一步付费生成的任务。**
- 为什么：在弱机器上并行启动 3D 软件会直接失败。
- 案例：一个通宵批次里，11 个镜头因为同时启动多个渲染进程而秒退。

**2.12 排查奇怪的效果时，先把那个物体单独渲出来测量，再猜原因。**
- 为什么：整场景里变量太多，单独渲染能一次定位问题。
- 案例：一个效果材质在整场景里不显示，单独渲染该物体后才找到原因。

## 3 关键帧

操作细节见 `04-keyframes.md`。

**3.1 AI 关键帧要做镜头的首帧、尾帧或主驱动，不要当成几张参考图之一；写实感必须已经在关键帧里，视频只负责"变化"。**
- 为什么：视频模型跟着最强的信号走，弱参考几乎不起作用。
- 案例：早期写实图只是五张参考图之一，提示词里还写了"不要用它的机位"，用户问为什么看不到这些图被用上；此后所有关键帧都在底图上重画，并当首尾帧用。

**3.2 关键帧在锁定的底图上重画：底图作为第 1 张图上传，产品母版图随后；成品统一裁成输出画幅的精确尺寸（横版 1920×1080、竖版 1080×1920），首尾帧尺寸一致、不超过输出分辨率。**
- 为什么：这样机位和产品位置不会变；分辨率过高会生出类似"指纹"的纹理，首尾帧比例不一致会把尾帧拉伸。
- 案例：用户从图像工具拿到的是 1672×941 的图，由脚本统一转成 1920×1080 再提交。

**3.3 每条画图提示词都带一段逐字相同的"统一设定"（产品、场景、光线、人物规则），由脚本逐字节核对；某张有例外，就单独写一行并标"本张例外"。**
- 为什么：图像工具的每个新对话互不记忆，一致性只能靠文字；不写明例外，全局规则会悄悄盖掉创作意图。
- 案例：两个灯光镜头需要墙面有光晕，单独写了"本张例外"，草稿一次通过。

**3.4 需要用户手工出图时，在同一轮回复里交一份完整的出图说明：每张图的提示词、按顺序上传哪些图、保存的文件名、检查清单，以及画偏时固定使用的一句纠正话。**
- 为什么：人工步骤可以复现、脚本能直接接手，用户也不用回头追问。
- 案例：有一轮 Claude 发完校样就结束了回合，用户只好追问「画图的指令呢？」。

**3.5 手工出图时一张图开一个新对话，最多纠正一次，不行就开新对话重画；一批图的前几张设检查点。**
- 为什么：同一个对话里越改越偏，前几张先把方向定住，能省掉整批返工。
- 案例：一批关键帧在第 2 张和第 5 张设了检查点，方向确认后再画剩下的。

**3.6 按视频平台的人脸政策设计关键帧：不画正脸（用背影、侧后方或让头出画）；人物身份只来自平台认可的来源，用原始文件或原始链接，不裁剪、不重新编码。**
- 为什么：不少视频平台会拒收写实人脸，改动过的人物图会失去"可信"身份。
- 案例：图像工具画的人物设定图带写实人脸，被视频平台拒收；改用同账号生成的人物原图后，所有关键帧都不露正脸。

**3.7 花视频生成的钱之前，先用免费的自动检查过一遍每张关键帧：产品轮廓、效果开关状态是否与底图一致、同一镜头几张图的缩放是否一致、产品数量、文件是否重复（校验和）。**
- 为什么：图像模型会自作主张开灯、改大小、多画一个产品；同镜缩放不一致，到视频里就成了没设计过的推拉。
- 案例：底图里灯是关的，模型画成了开着；同一镜头三张关键帧的缩放分别是 +9%、+4%、−8%；有一张图画出了两个产品，这个镜头弃用。

**3.8 画偏了先想办法救：只是缩放或平移偏了，就做图像配准对齐回底图再补边；画师的改动更自然、更安全时，改脚本去迁就画面。**
- 为什么：省掉一轮重画，也避免和模型较劲、反复重跑。
- 案例：一张结尾帧里的主机被画大了约 12.6%，配准后通过检查；另一张把人物画成背对镜头侧卧（正好藏住脸），保留下来并改写了提示词结尾。

**3.9 发现两张关键帧重复或缺图，先想能不能换生成模式（比如改用首尾帧），再考虑请人重画。**
- 为什么：换模式不花钱，重画要花用户的时间。
- 案例：校验和发现某镜头的两张关键帧字节完全相同，改用首尾帧模式，省掉一次重画。

**3.10 要同时出横版和竖版时，默认把英雄镜头（钩子、产品亮相、片尾产品镜头）按 9:16 原生构图、出关键帧、生成视频；从 16:9 裁 9:16 只用于次要镜头，而且要么生成横版时就把主体放进中间那条竖条，要么源素材是 4K。**
- 为什么：1920×1080 裁 9:16 只剩约三分之一的宽度，还要放大约 1.78 倍，明显变软；没提前规划的镜头，产品、人物和字幕的位置都会坏。4K 源裁完缩到 1080×1920 清晰度够用。
- 来源：通用实践；计算和做法见 `02-formats.md` 第 8.3 节。

**3.11 镜头关键帧之前，先画母版（look bible）：每件产品一张产品母版、每个场景时段一张场景母版、需要时一张人物设定图；每张过检查点、用户认可后，再画镜头关键帧，并把母版当作参考图上传。**
- 为什么：之后每张关键帧都照着母版画，母版错了，整批都要返工；先定母版，"统一设定"的文字也有了可以对照的画面。
- 案例：案例项目先画了产品母版和夜景、晨景两个房间母版，各过一次检查点后才画镜头关键帧，之后每张都把它们当图2、图3 上传。

**3.12 后补的镜头没有底图时，用一张已批准的关键帧当图1 重画，并在出图包里写"本张例外"改写统一设定第 2 条（"图1 是布景底图"）；这张图的检查改为和图1 比对，提交视频照常用首尾帧模式。**
- 为什么：不写明例外，统一设定第 2 条会让模型去找一张不存在的底图；没有遮罩和坐标，自动检查也要换参照。
- 案例：一个后补的镜头没有 3D 底图，用已批准的特写关键帧当图1，写明例外后一次画成，并按首尾帧模式提交。

## 4 视频生成

操作细节见 `05-video-gen.md`。

**4.1 每个镜头单独选生成模式：短的单一运动用首尾帧模式；长镜头，或镜头内的时间和方向很重要时，用多参考模式（关键帧 + 灰模视频）。**
- 为什么：两种模式通常互斥，首尾帧模式对两端严格对齐，多参考模式只算相对严格。
- 案例：短镜头基本用首尾帧模式，两个十几秒的长镜头用多参考模式。

**4.2 提示词只写"变化"：先写一句"保持首帧画面不变"，长镜头切成连续的 2–3 秒整秒段，每段只有一个主要变化，以"结束时……"收尾；不写亚秒级精度，也不写"生成一段 N 秒视频"。**
- 为什么：一段里塞得太多，模型会多切一刀或跳过动作。
- 案例：一个长镜头的提示词改成 7 个连续时间段后，第二版就通过了。

**4.3 参考包里只放你要它照抄的东西：不放机位不同的整屋图、带标注的走位图、带文字的设定图；每份素材写明用途和"不能从它身上拿什么"；每张参考图本身的产品细节必须正确。**
- 为什么：机位不同的参考图会变成模型可以"跳过去"的出口，参考图里的错误会被原样复制。
- 案例：一个镜头在 11.58 秒硬切到了参考包里那张俯视全景图；另一个镜头冒出一根错误的白色线缆，来自参考图里同样画错的线。

**4.4 写效果时按摄影机拍到的样子描述（颜色、表面上淡淡的反光、像热水杯口冒出的热气），避免"发光、光晕、光波"这类会凭空造出光源的词；材质颜色词注明"不发光"；常亮的灯写"亮度恒定、与首帧相同"，不写变暗、最低、呼吸；要灯关掉时写"在第 t 秒关闭，之后保持关闭"。**
- 为什么：模型会把没有边界的"发光"画成灯带，把"铜色"画成暖光，把任何变暗的动词理解成关灯。
- 案例：产品边缘亮成了 LED 灯带，整件产品一度变成一盏青色的灯；写了"降到最低"的灯在 2.5 秒熄灭，改成"亮度保持恒定"才通过。

**4.5 给效果定量：写清它真实从哪里出来、最大范围、留白（"上方空气保持清透"），再用一个肉眼可查的标准限定用量（"桌面木纹清晰可见"）。**
- 为什么：模型会自己发明效果的出处，还会用过量。
- 案例：一个效果先是从错误的位置冲出一根白柱，改了出处又铺满整个桌面，第三次把真实出处、最大范围和"木纹清晰可见"这条用量标准都写进去才对。

**4.6 提示词里的每个词都是指令：只点名画面里有的物体，位置以台面、墙、窗、柜子这类固定物为参照；禁用会改变任务类型的词（编辑、增加、删除、修改、延长、续写、继续）和没打算用的镜头词（全景、拉远、俯视、门口）。**
- 为什么：点名了但画面里没有的东西会被加出来，改变任务类型的词会把请求变成"编辑"或"续写"而失败。
- 案例：提示词里一句"门口"，让草稿凭空多出一道门；此后建了禁用词表，提交前自动检查。

**4.7 先用最便宜、不需要上传素材的镜头把整条 API 链路跑通；新的请求模式先付费试一条，再批量提交。**
- 为什么：花几块钱就能验证鉴权、请求格式、轮询和下载，避免整批失败。
- 案例：先单独试了一条首尾帧请求确认可用，再并行提交其余 9 条。

**4.8 一律先出低清草稿（如 480p）；审完、拼出粗剪、拿到用户明确同意后，才把批准的那几条用同一个任务升到高清（不重新生成）；升级放在顺序和字幕定稿之后。**
- 为什么：高清通常贵好几倍，而大部分问题在草稿阶段就能看出来。"同一任务升级"不是每个模型都有：没有这个功能时，高清就是重新生成，草稿只能当参考，剪辑点要重新量（`05-video-gen.md` 第 6 节）。
- 案例：反复重跑全在低清完成，定稿后一次升级 23 条，升级后画面与草稿的相关度为 0.993–0.998。

**4.9 每次付费提交前先 dry run（只拼请求、不发送），并设自动闸门：链接能访问且文件类型对、关键帧质检通过、人物素材没被改过、提示词与参考视频的效果时间线一致；缺质检报告时不提交。附带的视频客户端不读质检报告，这一条由项目自己的提交包装脚本或提交清单保证。**
- 为什么：生成之后才发现的错误，既花钱又花时间。
- 案例：提交前对照发现一个长镜头的提示词漏掉了一个效果；另一次 dry run 显示"拒绝：没有闸门报告"，等报告齐了才提交。

**4.10 付费调用链路要防中断：素材上传前压到平台限制以内（降码率、不降分辨率），临时链接的有效期当截止时间管理，提交和查询分成两步并记下任务号。**
- 为什么：链接过期或断网，会让付费任务失败或找不回来。
- 案例：一段 13.9 MB 的参考视频超过 10 MB 的上传上限，重编码到 4.0 MB；一次提交脚本断网崩溃，按日志里的任务号把两条草稿找了回来。

**4.11 重跑时给每个缺陷标上时间段，只改那几段提示词，一次只改一个变量，并保留旧版提示词。**
- 为什么：这样才知道是哪个改动起了作用。
- 案例：一个长镜头有三处问题（10–13 秒产品像灯、12–14 秒灯闪、11 秒嘴部僵硬），只改这三段，重跑一次就通过了。

**4.12 一个词出过事，就在所有提示词里搜这一族词，提前改掉。**
- 为什么：同样的词在别处会造成同样的失败。
- 案例：搜"最低、变暗、暗下、熄、呼吸"，在还没生成的另一个镜头里也找到并改掉了。

**4.13 反复失败的镜头果断弃用，让别的镜头承担它的作用。**
- 为什么：有些镜头不值得和模型较劲。
- 案例：一个总画出两个产品的镜头直接弃用，它要讲的内容由一个新镜头承担。

**4.14 4–6 秒的短镜头，如果颜色必须途经某个指定状态，或者运动中会露出首帧里没有的东西，就画一张中间关键帧，用"首帧 + 中间帧 + 尾帧"的有序关键帧模式生成（不带参考视频），不用首尾帧模式。**
- 为什么：首尾帧模式只锁两端，中间的颜色会自己找路（比如途经粉色），中途露出的东西由模型编。
- 案例：两个 4 秒镜头的颜色变化要按指定顺序走，改用三张有序关键帧、约 500 字的提示词后，颜色不再回退，也没有凭空冒出的物体。

> **模型备注（2026-10，使用前核对最新文档）**：案例项目用 Seedance 2.5 生成视频。当时它不接受含写实人脸的参考素材，人物图只认同账号生成、未改动的原图；参考视频要用公开链接；1080p 的公开单价约是 480p 的 5.5 倍。Kling、Runway、Veo、Hailuo 等其他视频模型的模式名称、时长上限和人脸政策各不相同，开工前逐一查官方文档。

## 5 审片与记录

操作细节见 `05-video-gen.md`（审片）和 `10-working-with-user.md`（brief 与记录）。

**5.1 参考视频上传前、草稿交给用户前，都用联系表（一张图排满多帧）和逐秒对照图过一遍。**
- 为什么：联系表一眼就能看出遮挡、跳变和颜色问题，比来回播放快得多。
- 案例：联系表显示一段参考视频的开头被替身挡住了镜头，上传前就重做了。

**5.2 剪辑前逐帧看草稿原片（每 0.25 秒一帧，配运动量和亮度曲线），专门找硬切、内部叠化、定格，以及产品轮廓、字样和接口方向的漂移。**
- 为什么：漂移是随时间出现的，一帧好不代表整条好；首尾帧模式会在两张构图略有差异的关键帧之间偷偷做叠化。
- 案例：一条草稿在 2.25–3.4 秒有内部叠化，画面里出现两个插头，以及袖子和头发的重影。

**5.3 逐帧查产品上的 logo、字样和图标有没有被画乱；乱了就换不露字的角度，或在剪辑层贴片修，不要放进成片。**
- 为什么：视频模型画小字很不稳定，乱码字会让产品看起来像假货。
- 来源：通用实践；案例里的对标片就出现过乱码字。

**5.4 每次集成后安排一个独立的"挑刺"审查，它必须看生成的原片，不能只看剪好的成片；修完后，把所有陈述同一事实的文档都复查一遍。**
- 为什么：集成的人会漏看原片里的问题；只改一处文档，文档之间会互相矛盾。
- 案例：独立审查在原片里发现了集成时漏掉的重影，共提出 7 处修改；人物改用左手之后，流程文档里还写着旧动作。

**5.5 派 agent 前，把用户反馈按原话（用「」引用）编号写进 brief，并设一节"当前定稿"作为唯一依据；每轮评审做成表：意见 → 采纳或改动（附理由）→ 改在哪里 → 由哪个闸门验证。**
- 为什么：转述会走样；长会话会被压缩，文件不会。
- 案例：第二轮修改的 brief 累积了 16 条按原话编号的硬性要求，终审逐条对照。

**5.6 自动质检闸门先用"已知好"和"人为制造的坏"两类样本校准；它判失败时，先截图逐帧核实，再决定要不要花钱重跑。**
- 为什么：闸门会把图像模型合理的重新诠释误判成失败。
- 案例：第一次校准时连底图本身都只有 30/42 张通过；视频闸门报"灯在闪"，实际是机位移动时跟踪器丢了目标。

**5.7 人工放行要写理由、存进闸门报告、绑定图片的文件指纹（校验和）；不要靠放宽阈值了事。**
- 为什么：悄悄绕过会丢掉审计记录；图片一改，放行就该失效。
- 案例：5 张误判的关键帧按文件指纹记入人工放行记录，图一换就要重审。

**5.8 每次方向调整和来之不易的方法，立刻写进项目记忆和决策文件；说错的地方，书面更正。**
- 为什么：防止上下文被压缩或额度中断之后，又退回老路。
- 案例："AI 出最终像素"这一决定当天就写进了记忆，撞到用量上限停了几天，回来后能直接接着做。

**5.9 生成脚本是唯一来源：谁手改了脚本生成的文件，就在脚本上标"不要重跑"，直到改动搬回脚本。**
- 为什么：不然重跑一次，会悄悄抹掉手工更正。
- 案例：两个生成脚本的输出被手工补过内容，于是在文档里注明这两个脚本暂停重跑。

**5.10 项目第一天就建版本管理（git）；规格、镜头表、字幕、EDL 各自只有一个源文件，说明文档从它们生成，或标明"已被取代"。**
- 为什么：同一个事实存在好几处就会对不上，没有版本管理，每次改动都得手工备份。
- 案例：项目当时没用 git，出现过流程文档和字幕文件各写一个版本、剪辑器读错字幕文件的情况。

## 6 剪辑与转场

操作细节见 `06-edit-type.md`。

**6.1 把剪辑写成数据：一份 EDL 决定每个片段的出入点、速度、转场和字幕文件，由程序照着出片；EDL 自己声明用哪些数据文件。**
- 为什么：改顺序、改字只需改数据后重跑，程序读错文件的问题也就没有了。
- 案例：第一版粗剪只是把镜头按顺序拼起来，用户说「每一次视角切换和转场都非常生硬」，于是改成 EDL 剪辑器。

**6.2 生成镜头之前，先把每个衔接点设计好并写下理由：只有同一空间、同一时刻、画面里没有脸时，才用 AI 衔接镜头；其他情况用有动机的剪辑转场（叠化、光晕、甩镜、黑场）。**
- 为什么：跨光线、跨主体、跨人物或画面有脸的 AI 衔接镜头容易失败。
- 案例：转场表计划了 5 个 AI 衔接镜头，成片用了 2 个，其余接口用设计过的转场。

**6.3 衔接处运动要连续：衔接镜头的运动节奏和前后镜头匹配，用实测的运动阈值定出点；不要把静止画面叠化进已经在动的镜头，先回到完全相同的定格帧再切。**
- 为什么：运动不匹配会产生"停一下再走"的顿挫或重影。
- 案例：有两处衔接出现了"停了再走"，按实测运动量把一个出点从 3.4 秒改到 3.2 秒。

**6.4 只用草稿里构图单一、干净的那一段；不够长就放慢，残留的重影藏进短叠化里。**
- 为什么：首尾帧草稿内部常有隐藏的构图过渡。
- 案例：一条草稿只用了前 2.25 秒并放慢到约 0.58 倍，另一条放慢到 0.75 倍。

**6.5 渲染后检查每个衔接点前后的帧（拼一张衔接对照图）；转场强度和章节卡时长在真实预览里调；同一句话不要既做标题卡又做字幕。**
- 为什么：默认参数常常过头，黑场会把很短的卡片"吃掉"。
- 案例：光晕转场几乎把整帧刷白，降到 0.8 秒、强度 0.6；一张章节卡被两侧黑场吃到只剩约 0.5 秒，还和字幕重复，改为只叠字。

**6.6 后期小改要像外科手术一样精准：每一项都能单独覆盖参数，片段按内容指纹缓存，改一个标题只重渲那一张卡。**
- 为什么：用户最担心的是「需要全部推翻再重新来吗？」。
- 案例：改片头标题时只重渲了标题卡，再重新合成音轨。

**6.7 〔广告〕节奏跟音乐走：先定音乐并标出节拍点，剪点落在拍点上；产品亮相、卖点证明和片尾卡落在重拍或乐句起点。**
- 为什么：卡在拍点上的剪辑显得利落，关键画面借着音乐的重音被记住。
- 来源：通用实践。

**6.8 〔广告〕快节奏靠剪辑做出来，不靠在生成镜头里加快运镜：用更多、更短的镜头切，每个生成镜头内部仍是慢速、单方向的运动。**
- 为什么：视频模型在快速或组合运镜下最容易变形和漂移（见 1.7）。
- 来源：通用实践。

## 7 字幕、标注与排版

操作细节见 `06-edit-type.md`。

**7.1 字幕、标注、片头卡、logo 和片尾卡都作为剪辑层的叠加，不烧进生成的画面，也不让模型去画。**
- 为什么：改字、换语言、升级高清都不必重新生成画面，而模型画的字和 logo 不可靠。
- 案例：高清升级和声音制作同时进行，最后再合成；改标题时只重渲了一张卡。

**7.2 每条字幕按它出现期间的画面定位置：选安静的留白，放在主体的对侧，不压住产品、人物或正在演示的效果；在真实草稿上复查，不只在灰色底图上定。**
- 为什么：固定位置会和构图打架，底图和真实画面也有出入。
- 案例：用户说「字幕也不要全部出现在同一个位置」；一条在底图上定好的字幕，到真实草稿上盖住了耳朵和头发，重新排了版。

**7.3 给阅读时间做预算：单行字幕至少 2 秒、两行至少 3 秒，两条之间至少隔 0.6 秒，与转场的重叠不超过 0.2 秒，字幕和标注不同时出现；放不下就改剪辑（放慢、加停留），不改规则。**
- 为什么：读不完的字只是噪音。
- 案例：重排后两条字幕只隔 0.38 秒，挪开后才通过；一个镜头放慢到 0.8 倍，才放得下两行字幕。

**7.4 逐条出现的标注，要满足"起始时间 +（条数 − 1）× 间隔 + 1.5 秒"放得进片段；每次重排后重跑间隔检查。**
- 为什么：最后一条标注也要有读完的时间。
- 案例：一张透视图的标注全部出齐后只停留 1.2 秒，于是缩短间隔、把结尾定格加到 5 秒。

**7.5 〔讲解片〕爆炸图和透视图里，每个看得见的结构都配一条引导线（名称 + 一句功能），不要合并；锚点用 3D 坐标经机位投影算出，再在批准的草稿上复测。**
- 为什么：投资人会把剖视图当规格表看，手工摆的锚点会偏。
- 案例：一张透视图的标注从 5 条合并标注拆成了 11 条；投影出的锚点与实测位置相差不到 0.1 像素。

**7.6 字体层级（重点词、换行、级别）写在数据里，由一个排版引擎统一渲染；按交付分辨率、用真实字体、以 1:1 尺寸出校样检查。附带排版引擎的默认色板和字体只是占位，换成品牌自己的；能沿用的是层级和字号比例。**
- 为什么：全片风格一致、改字不用手排，而缩略图看不出字号和字形问题。
- 案例：用户要求重点字放大、一般字缩小，做出错落感；1:1 校样里发现"一一展开"在细体字里像破折号，改成"依次展开"。

**7.7 全片锁定命名：功能或卖点的名称和顺序在每一幕、每张卡上完全一致；来自语音输入的品牌名和产品名逐字确认。**
- 为什么：观众要学会这套叫法，名称一变就乱；品牌名印错代价很大。
- 案例：几项功能定为固定的单字称呼，两幕里顺序相同；语音转写出来的品牌名有同音错字，逐字确认后才上屏。

**7.8 把全部字幕当成一个序列通读：查重复的关键词、不成对的章节名，以及片头卡和字幕是否说了同一句话。**
- 为什么：一条一条地写，看不出重复。
- 案例：同一个关键词出现了好几次，两个章节名一个说时间、一个说状态，不成对，改成都说时间；两个部件做同一件事时，改成先出现的说"做什么"、后出现的说"怎么补强"。

**7.9 技术型说法写定性事实并点名具体技术，感受型说法才用情绪化表达；不用"感知""黑科技"这类含糊词。**
- 为什么：诗意的技术描述显得空泛，懂行的观众要看到具体技术。
- 案例：灯光字幕从一个诗意的形容词改成了写实的光色描述；用户要求字幕写出所用具体技术的名称。

**7.10 〔广告〕把 logo、品牌色、字体、产品名写法和口号写进一份品牌设定文件，所有版本和剪短版都从它取值；logo 一律用官方矢量文件叠加。**
- 为什么：多个版本各自手调，颜色、字体和写法很快就不一致。
- 来源：通用实践。

**7.11 竖版（9:16）的字幕、logo、CTA 和产品关键部位都放进保守安全框：上留 15%、下留 35%、左留 6%、右留 10%（1080×1920 上约为 x 65–888、y 288–1248），投放前再用平台官方模板核对。**
- 为什么：竖屏的状态栏、点赞按钮列、账号名和文案会盖住画面边缘，被盖住的 CTA 等于没有。
- 来源：通用实践；各平台数值和出处见 `02-formats.md` 第 5、9 节。

**7.12 换画幅时，字幕、标注和 logo 按新画幅重新排版，并重跑位置、间隔和安全区检查，不要整体缩放横版的文字层。**
- 为什么：横版的位置理由在竖版里大多不成立，整体缩放后字也会太小。
- 来源：通用实践。

## 8 合规

操作细节见 `09-compliance.md`。

**8.1 每一句上屏文字和配音稿在渲染前都过词表闸门：不出现未经证实的规格数字、功效或医疗说法、最高级和绝对化表述，也不夸大感知能力；产品所属品类的功效词同样不用。**
- 为什么：健康、儿童、金融这类品类有监管和信誉风险，闸门能抓住人眼漏掉的词。
- 案例：一个规格数字和一句绝对化说法被改掉；标题里的品类功效词改成了中性说法。

**8.2 词表闸门抓不住"暗示的功能"，要逐句对照功能事实文件：只写画面确实演示了的、产品做了什么，不写对人产生了什么效果。**
- 为什么：一句话可以完全不含禁用词，却暗示了产品没有的功能。
- 案例：一句配音通过了闸门，却暗示产品会自动启动，而首版并没有这个功能，于是删掉；一句英文标语暗示与自然现象同步，改成了比喻说法。

**8.3 另列一张"设计目标 vs 已实现 vs 可公开"清单（`brief/claims.md`，模板 `templates/claims.md`）：讲解片里未实现的功能只作设计示意、不配数字；〔广告〕里只展示买到手就有的功能。**
- 为什么：投资人片可以展示路线图，卖货的广告展示了就等于承诺。
- 案例：讲解片里几处连续变化的效果属于设计目标，已在清单里标出，对外使用前要再确认；广告部分为通用实践。

**8.4 合规顾虑要摆到桌面上让用户决定，不要悄悄把产品说法写弱；说法由产品方定，措辞由 Claude 把关（用"感知、捕捉"，不用医疗动词）。**
- 为什么：悄悄写弱会歪曲产品，而说法是产品方的决定。
- 案例：Claude 因为文档里写着某项指标尚未验证，就自行把字幕只写成一项；产品方指出几项都能捕捉，改回了完整说法。

**8.5 按发布地规定和平台要求标注 AI 生成内容，默认三处：开头画面一行简短 AI 标识（至少约 2 秒），片尾小字说明一次（如"画面由 AI 生成 · 部分功能为视觉示意"），上传时勾选平台的 AI 声明；不挂常驻角标，除非平台要求。**
- 为什么：画面中间保持干净，开头和结尾都有标识，满足"起始画面"提示的要求，也避免示意效果被当成真实演示。
- 案例：用户要求去掉画面角落的 AI 标识，改为片尾一行"影片由 AI 生成 · 产品功能为视觉示意"；之后本 skill 的默认改成"开头 + 片尾 + 平台声明"（`09-compliance.md` 第 4.2 节）。

**8.6 商用片走企业 API 或经过认证的商用账号，不用条款禁止商用的消费级 App；画面里的人物用 AI 生成，不用真人脸，也不做得像某位名人。**
- 为什么：消费级条款常禁止广告用途，平台也会拒收真人脸，像名人就有肖像纠纷。
- 案例：开工调研时就定下"企业 API + AI 生成人物"，全片没有一张真人脸。

**8.7 〔广告〕不造假证言和假评价：不用 AI 生成的"顾客""专家""医生"说推荐语，不编造评分、销量、奖项和用户数；演绎的场景要让人看得出是演绎。**
- 为什么：这在很多地区都属于虚假广告，例如美国 FTC 2024 年发布的评论与推荐规则就明确涵盖 AI 生成的假评价。
- 来源：通用实践。

**8.8 〔广告〕价格、优惠、日期、网址、二维码这类时效信息放在剪辑层，交付前逐条核对，在交付说明里写明有效期，并确认投放平台允许画面里出现二维码和外链。**
- 为什么：过期或写错的价格就是虚假宣传，最容易在改版时漏掉；不少平台禁止画面里放二维码和外链。
- 来源：通用实践。

**8.9 〔广告〕比较类说法（比某某更好、第一、领先）要有可公开核实的依据；不点名贬低竞品。**
- 为什么：比较广告是投诉和监管的高发区。
- 来源：通用实践。

**8.10 每个外部素材（音乐、音效、字体、图片）都记进 `brief/licenses.md`（模板 `templates/licenses.md`）：来源、作者和许可证；广告要确认许可覆盖商业广告和付费投放；CC BY 素材按要求署名，剪辑过的注明"(edited)"。**
- 为什么：很多"免版税"许可不覆盖广告投放或广播，字体也常要单独的商用授权。
- 案例：用一份来源与许可表记录每个素材，配乐按 CC BY 要求署名进片尾；查不到许可的素材写"未核实"，不进成片。

**8.11 对外公开的内容不露产品内部：不放爆炸图、透视图和能看到内部结构的半透明镜头，不写内部元件名称和工作原理；广告默认就是公开内容。**
- 为什么：投资人片可以讲技术细节，公开内容会泄露技术方案。
- 案例：用户准备把片段发社交平台时，要求去掉所有爆炸图、透视图和能透露技术细节的画面。

## 9 声音

操作细节见 `07-sound.md`。

**9.1 画面和声音分开做成独立音轨，最后再合成；音效按"某镜头第几秒"挂在 EDL 时间线上，从当前时间线读取，不写死镜头顺序。**
- 为什么：音频小改只要几分钟、不用重渲画面，写死顺序的脚本在重排后会直接崩溃。
- 案例：重排镜头后，一个音效的时间窗还按旧顺序算，算出负长度，脚本当场崩溃。

**9.2 剪辑结构一定下来就开始做声音，和画面并行。**
- 为什么：声音拖到最后，混音问题就只能在交付后返工。
- 案例：声音阶段在画面全部通过后才开始，交付第一版后又因为音乐盖住提示音而重混了一版。

**9.3 优先用产品自己的声音素材，用之前先分析频谱、持续音和电平。**
- 为什么：更真实，也能提前发现会被听成嗡嗡声的持续音。
- 案例：用户提供的一条素材里有两个约 250 Hz 的持续音，占了一半以上的能量，提前告诉了用户。

**9.4 每个声音都是一个"谁在动作"的声明：自动亮起的灯没有开关声，不该出现的环境声不出现；安静型产品默认无声，只放有目的的提示音。**
- 为什么：多余的声音会讲错故事。
- 案例：音效清单逐条写明"谁在发声、为什么"，删掉了不该有的开关声和抢戏的窗外鸟叫。

**9.5 环境底噪随场景一起结束，提示音要低而柔。**
- 为什么：一层从中段响到结尾的底噪会被听成噪音，尖锐的提示音会被听成报错。
- 案例：用户嫌标注提示音太尖、底噪一直没去掉，换成柔和低沉的木槌音并删掉了底噪。

**9.6 音乐按场景剪：在乐句或换气处切，接点放在两段共有的和弦上，用持续音衔接而不是淡出后留静音；音乐事件落在画面事件上，最后一句落在片尾卡。每个接点导出一个 20 秒的试听文件（接点前后各 10 秒）发给用户听。**
- 为什么：调性一变，只靠音量渐变听起来仍然突兀。
- 案例：用户指出过渡「在曲调方面也是需要有和谐的过渡的」，改为在共同和弦上做 3 秒交叉淡化；独立音乐审查提出 8 个问题，6 个属实，全部修好。

**9.7 实测配乐的调音和调性（不信粗略的估计工具），把所有有音高的音效移到这个调上。**
- 为什么：音效和音乐不在一个调上会打架。
- 案例：估计工具给出 443.8 Hz，实测是 440 Hz；提示音随之改到配乐的主音上。

**9.8 按时间窗实测平衡：测每个音效窗口里"音效减音乐"的 dB 差，先给音乐小幅整体衰减，再在窗口内闪避（约 0.6 秒渐变）；闪避量写成相对于没有预先压低过的音乐分轨的总量。短提示音按每个约 60 ms 逐个测，逐个测仍比音乐低 8 dB 以上就直接提升它；在完整混音上判断。**
- 为什么：整体推音量救不了被掩盖 30 dB 的声音，渐变能防止音乐忽大忽小；整段平均会把被盖住的单个提示音藏起来；音乐分轨里已经压过的那部分不算进去，新分轨就会压得不够。
- 案例：用户说音乐太强，按窗口测量后，一段产品声从比音乐低 13.2 dB 调到低 4.2 dB；标注段按整段平均改善了约 8 dB，逐个测时提示音仍低 10–16 dB，于是把提示音本身提升了 6 dB。

**9.9 母带响度按交付平台定：网络视频约 −14 到 −16 LUFS、真峰值约 −1 到 −1.5 dBTP；广播电视按当地标准（如欧洲 EBU R128 为 −23 LUFS，美国 ATSC A/85 为 −24 LKFS）。完整的表见 `07-sound.md` 第 9 节。**
- 为什么：响度不对，平台会自动把片子压低，或者在一串广告里显得突兀。
- 案例：讲解片母带做到约 −16 LUFS、−1.5 dBTP，中英两版一致；广播标准部分为通用实践。

**9.10 配音宁少勿多，不在配音里加入字幕和事实文件之外的新说法；配音稿和上屏文字一起过合规。**
- 为什么：信息重复显得啰嗦，配音里多出的一句话同样是对外宣称。
- 案例：讲解片的信息全部由字幕承担，最后决定不配音。

**9.11 用 AI 配音前先做盲听 A/B：和真人录音样本把响度对齐后试听，用户分不出来才用；分得出来就换真人配音员，或者不配音。**
- 为什么：一听就假的声音会让整支片显得廉价。
- 案例：用户要求"非常真实的真人声音"，A/B 样本统一到 −18 LUFS 试听后，用户决定不要配音。

**9.12 不克隆任何真人的声音；要用某个真人的声音，就请本人录音并签书面授权；只用有商用授权的合成声音或签约配音员，并保存授权记录。**
- 为什么：克隆声音涉及本人的声音权益和平台政策，多数地区都需要本人明确同意。
- 来源：通用实践；案例项目开工时就定下了"不克隆真人声音"。

**9.13 〔广告〕配音字数按时长做预算：中文约每秒 3–4 个字（快节奏到 5 个），英文约每秒 2.5 个词，开头钩子和片尾卡要留出空隙；超了就删字，不加速念。**
- 为什么：赶着念的配音听不清，还会挤掉片尾卡。
- 来源：通用实践。

**9.14 配乐优先用授权清楚的曲库或委托创作；用 AI 生成的音乐前，确认工具的商用条款和发布地对 AI 作品版权的立场。**
- 为什么：AI 音乐的版权归属在很多地区还不明确，广告投放后被下架代价很大。
- 案例：讲解片选曲时没有用 AI 生成音乐，原因就是版权保护不确定。

## 10 交付与多版本

操作细节见 `08-delivery.md`。

**10.1 至少交两档：放映或投放用的高码率母版，和压到常用聊天工具附件上限以内的分享版；发送前核对时长、音视频流、响度，以及字幕出现时刻的画面。**
- 为什么：路演现场和手机转发需要不同的文件，没核对过的分享版可能音画不全。
- 案例：约 65 MB 的母版发不到手机，另出了 29 MB 的分享版。

**10.2 多语言版本由一份文案文件生成平行的字幕、标注和 EDL，画面、剪辑和音乐都不动；渲染后扫描时间线，确认没有残留的原语言字符。**
- 为什么：又快又安全，检查结果可以证明，不靠肉眼。
- 案例：英文版只重渲文字层，约 5 分钟出片，残留中文字符为 0。

**10.3 渲染器新增的选项默认保持原有行为，用像素级比对证明原版没变。**
- 为什么：加功能时最容易悄悄改坏已经交付的版本。
- 案例：加入英文排版开关后，28 个中文输出逐一比对，0 个有差异。

**10.4 文案长度上限按版面几何算（每侧多少像素）；拉丁文字按渲染后的像素宽度检查，不按字数；字号在 1:1 的真实画面裁切图上判断。**
- 为什么：按中文字数定的上限用在英文上会误判，溢出本质上是像素问题。
- 案例：按中文字数规则报出的 28 条告警全是误报；英文关键词在原尺寸裁切图上偏小，从 24 px 调到 26 px。

**10.5 对外文案按这条流程走：多人并行起草 → 评审合并 → 合规核查 + 母语核查 → 独立终检；翻译稿要单独做一遍合规。**
- 为什么：直译会生出新的说法和别扭的表达。
- 案例：英文终稿查出了一个词像俚语、"non-slip"属于绝对化、一句标语暗示了对身体的作用等问题。

**10.6 混音、编码这类后处理步骤先单独跑通一遍，再接到长时间渲染后面；优先用环境里已经有的库。**
- 为什么：接在长渲染后面才崩溃，整条链都白跑。
- 案例：高清画面渲完后，紧接着的混音因为引用了没安装的库而崩溃，只好重跑。

**10.7 〔广告〕30 / 15 / 6 秒剪短版都从同一份主 EDL 派生（只列出选用的片段和时长），共用音乐、字幕样式和片尾卡；每个版本单独检查钩子、品牌露出和 CTA。**
- 为什么：各自手剪会让版本之间不一致，改一处要改好几遍。
- 来源：通用实践。

**10.8 〔广告〕把每个投放平台的规格写成一张表：画幅（16:9 / 9:16 / 1:1 / 4:5）、时长上限、文件大小、响度、要不要烧录字幕、封面帧；渲染脚本照表批量出。**
- 为什么：平台规格各不相同且常变，写成数据才能一次出齐、改一处全部更新。
- 来源：通用实践。

**10.9 〔广告〕第一帧就要能当封面：用清楚的产品或钩子画面开头，不用黑场或淡入。**
- 为什么：很多平台拿第一帧当预览图，自动播放也从第一帧开始。
- 来源：通用实践。

## 11 协作、成本与安全

操作细节见 `10-working-with-user.md`。

**11.1 开跑前讲清预算、计价公式、上限，以及套餐或节省计划真实能抵扣多少；每次生成都记账，每批之后报告"已花多少 / 上限多少"。**
- 为什么：避免中途欠费，账单也能独立对上。
- 案例：高清升级用光了一个节省计划的抵扣额度，账户转为欠费，最后靠自己的生成日志对上了平台账单。

**11.2 每次大批量生成（批量草稿、尤其高清升级）前，先报价、留余量，并请用户看一眼账户余额和套餐的真实抵扣额。**
- 为什么：只核对预算上限、不核对余额，平台会在中途以欠费为由拒绝任务。
- 案例：一次新镜头提交被平台以欠费为由拒绝，原因是升级前只核对了预算上限，没看余额。

**11.3 绝不读取、回显、索要或记录密钥：密钥只放在本地 .env 文件里，检查时只看变量名、长度，以及一个免费只读接口是否返回正常。**
- 为什么：用户不写代码，又在用付费密钥，安全必须由流程保证。
- 案例：用户把密钥存成了一个以密钥命名的空文件，.env 里却是空的；Claude 只给操作步骤，并只验证长度和接口返回，不显示内容。

**11.4 在付费控制台里遇到同意协议、付款、开通服务、下载文件，都先停下说明代价，等用户明确同意；不创建账号，不输入密码或支付信息。**
- 为什么：这是安全边界，也是用户的信任所在。
- 案例：开通视频模型服务需要同意 4 份协议并预付一笔费用，Claude 停在确认按钮前，等用户回复确认后才继续。

**11.5 不让两个 agent 同时改同一个文件，第二个排队；新反馈改变了刚启动的工作流的范围时，停掉它，合并 brief 后重启；不再需要的后台工作流及时停掉。**
- 为什么：同时改会冲突，带着旧范围跑完再补比重启更贵，空跑浪费额度。
- 案例：排版 agent 排在标注 agent 之后；一个工作流刚启动就因新反馈停掉，合并要求后重启。

**11.6 工作流要能续跑：脚本放在项目文件夹里，每一步结果写到磁盘；把用户的手工步骤安排在额度冷却或长渲染期间做。**
- 为什么：额度上限、断网和电脑睡眠会反复打断长任务。
- 案例：撞到每周用量上限停工的几天里，用户画完了全部 42 张关键帧；断网后，两个工作流从磁盘上的中间结果接着跑。

**11.7 长时间无人值守渲染前，请用户插上电源并把系统睡眠设为"从不"（系统设置由用户自己改），同时申请保持唤醒。**
- 为什么：保持唤醒只在会话活跃时有效，笔记本睡着了，渲染就停了。
- 案例：笔记本夜里进入睡眠，渲染停了约 9 小时。

**11.8 长任务的第一句回复就给出预计时长和完成时刻，按阶段列出（包括用户要做的步骤），一旦延误马上更新；后台久无可见输出时，主动报告当前阶段和预计时间。**
- 为什么：用户要按这个安排自己的时间，看不到进展会以为任务卡住了。
- 案例：用户反复问"还要多久""你还在运行吗"，直到每轮第一句都给出分钟数和完成时刻才不再追问。

**11.9 给不写代码的用户的东西要能直接用：设计文档变成附带费用和时间的决策清单，只有用户能做的操作给逐步说明，交付能直接打开、播放的文件而不是网页链接。**
- 为什么：说明含糊会导致操作出错，链接可能打不开，文字描述也没法试听。
- 案例：选音乐时只发了网页地址，用户说「你根本就没有给我试听的链接呀」，改为直接发音频文件。

**11.10 听清用户要的工作方式：说"先分析"就只分析；说"中间不要停"就一路做到交付；说是最后一轮就跳过中间试听；用户问"要不要推翻重来"时，第一句先给结论。**
- 为什么：节奏由用户掌握，结论先行才能让用户马上做决定。
- 案例：同一个项目里，"先不要执行任何操作"和"中间你就不要停了"两种指令都出现过。

**11.11 每轮意见先编号成表再动手；一条意见牵动多个文件时，先列出受影响的文件清单，改完逐个核对。**
- 为什么：一句口头意见往往同时影响 3D、提示词、字幕和声音，漏一处就会在下次生成时回来。
- 案例：一次镜头顺序调整同时牵动了 EDL 顺序、字幕间隔、音效时间窗和音乐转场，逐项核对后才通过。

**11.12 时间紧时，先找电脑里已有的模型和工具，再考虑公共演示站或新下载。**
- 为什么：公共演示站会排队，本地的东西更快，也不依赖网络。
- 案例：在线配音演示站排队或超时，改用电脑里上一个项目留下的本地模型，几分钟就出了样音。

**11.13 脚本按跨平台来写：Python 用 uv 运行并设 UTF-8 输出，路径用 pathlib，ffmpeg 从 imageio-ffmpeg 获取，复杂改动写成脚本文件而不是命令行长文本；改完立即做语法检查或 dry run。**
- 为什么：编码、路径和换行符的差异，每一条都至少让一次运行失败过。
- 案例：在 Windows 上先后出过打印中文时崩溃、命令行长文本被截断、行尾 \r 导致 JSON 解析失败等问题。

## 规则怎么维护

- 新项目踩到新坑：按同样格式（做法一行、为什么、案例或来源）加到对应组的末尾，编号接着排，不改已有编号，因为 `pitfalls.md` 和其他文件按编号引用。
- 只对某个产品成立的事实（尺寸、机理、命名），写进那个项目自己的事实文件，不写进这里。
- 标着"来源：通用实践"的规则，在真实项目里验证过之后，可以补上一句案例。
- 模型和平台的具体限制只写进带日期的"模型备注"，过期就更新或删掉。
