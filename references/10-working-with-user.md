## 1. 沟通

### 1.1 时间预估放在第一句

- 长任务（超过约 10 分钟）的第一条回复就写：要多少分钟、几点完成（本机时钟时间）、分几个阶段、哪些步骤要用户自己做、用户要等多久。
- 延误了马上给新的完成时间和原因，不要等用户问。
- 后台长时间没有可见输出时，主动报一句进度。格式：

  > 进度：第 3/5 阶段（生成草稿）。最后一次活动 14:32（第 6 条草稿已下载）。预计 15:10 完成。如果跳过独立复审，可以提前约 15 分钟，但会少一道检查。

- 用户问"还要多久""还在跑吗""电脑没睡吧"，说明时间给得不够清楚，或者进度报得太少。

### 1.2 结论先行

- 用户问"要不要推翻重来"这类问题，第一句给结论（"不用，只要重渲片头那一张卡"），再讲理由，最后列出需要他拍板的点。
- 报告的顺序：结论 → 依据 → 需要你决定的事（附推荐）→ 下一步和时间。

### 1.3 轮到用户动手时，一次交齐

- **说明文件和请求放在同一轮回复里**，不要发完校样就结束回合。说明文件写清：要做什么、按什么顺序、每一步用哪些文件（写路径）、结果存成什么名字放在哪、做完怎么自查、出问题时说哪一句固定的话、做到哪里停下来给 AI 助手看。出图说明的写法见 `04-keyframes.md`。
- **要用户看或听的东西，直接发能打开、能播放的文件**（mp4、mp3、png、pdf），不要只发网页链接或文字描述。用户没法在一段文字里试听音乐。
- **发到手机的文件控制在 30 MB 以内**（远程发送的上限，见工具备注）。更大的母版，告诉用户它在哪个文件夹、叫什么名字，另做一个 30 MB 以内的分享版。
- **只有用户能做的操作**（登录、开通、贴密钥、改系统设置），写成逐步点击和粘贴的说明，具体到菜单名和按钮名。

### 1.4 听清用户要的工作方式

| 用户说 | 意思 | AI 助手怎么做 |
|---|---|---|
| 「先不要执行任何操作，先分析」 | 只分析 | 只读、只回答。不改文件，不花钱，不启动任务 |
| 「中间你就不要停了」 | 一路做到底 | 按已批准的方案做到交付，中途不等确认。超出已批准范围的花费、同意协议、付款、下载，仍然要停 |
| 「这是最后一轮」 | 跳过中间环节 | 不再出中间试听和低清预览，直接出成片；交付前的自检照做 |
| 「先不升级，等 X 出来再说」 | 暂停某一步 | 记进决策清单，条件满足时主动提出来 |

### 1.5 批准要留下用户的原话

- 用户每放行一件事（选路线、批准草稿、放行高清升级、定稿字幕），记一条：日期、事项、用户原话（用「」引用，一字不改）、对应的文件和它的指纹（sha256，文件内容一变它就变）。
- 记在哪里：决策和放行的原话写进 `brief/decisions.md` 的"决定记录"（模板 `templates/decision_list.md`）；批准了哪一条草稿写进批准账本 `edit/approved_drafts.json`、`edit/approved_bridges.json`（剪辑只从账本取素材，见 `05-video-gen.md` 第 13 节）。
- 文件一改，指纹就变，对应的批准自动失效，要请用户重新看。
- 一条批准记录的例子：

  ```json
  {
    "date": "2026-10-22",
    "item": "upgrade approved drafts to 1080p",
    "user_quote": "这几个镜头的顺序和字幕都改好之后，就可以升级到 1080p 了",
    "condition": "order and captions final",
    "files": {"edit/edl.json": "sha256:3f9a...", "edit/approved_drafts.json": "sha256:7c21..."}
  }
  ```

### 1.6 意见编成号，写进 brief

- 每轮意见先编号成表，再动手，写进 `brief/feedback_brief.md`（模板 `../templates/feedback_brief.md`）。
- 用户原话照抄，用「」引用；下面写"执行规则"和"影响哪些文件"。
- 设一节"当前定稿"作为唯一依据；被推翻的旧规则移到"已被取代"，不删。
- 派子任务（agent）之前，把 brief 的路径写进它的任务说明。所有 agent 和终审都逐条对照它。
- 原因：转述会走样；长对话会被压缩成摘要，文件不会。
- 一条意见常常牵动好几个文件（3D、提示词、字幕、声音），先列出受影响的文件清单，改完逐个核对。

### 1.7 用决策清单，不用设计文档

- 给不写代码的用户，不发长设计文档，发一页决策清单，存成 `brief/decisions.md`（模板 `../templates/decision_list.md`）。每个选项写清费用、时间、风险和推荐。
- 能自己定的小事直接定，列在"我直接定的"那一节，让用户知道并可以推翻。

### 1.8 人机并行

- 等待的时间（平台排队、账号额度冷却、长渲染）正好安排用户做他的手工步骤：画关键帧、选音乐、准备产品自带的声音素材。
- 画面和声音可以并行：剪辑结构一定下来，就开始选音乐、整理产品声音。

> 案例：某产品片做到一半，AI 助手的每周用量额度用完，停了 4 天。创始人趁这几天画完了 42 张关键帧，恢复后直接进入视频生成。

## 2. 安全边界

这些边界在用户催促、说"你直接帮我弄"时同样成立。

### 2.1 密钥

- 不读取、不回显、不索要、不记录密钥的内容。
- 密钥只放在 `.env`，`.env` 写进 `.gitignore`。
- 检查时只看：变量在不在、长度合不合理、一次免费只读接口是否返回正常。打印时只显示"已设置（长度 N）"。
- 脚本日志里不打印请求头；报错信息打印之前，去掉带签名的链接里的查询参数。
- 临时链接用脚本从剪贴板直接写进 `.env`，不经过聊天。
- 用户把密钥贴进了聊天、或者密钥出现在文件名里：按泄露处理，请他到控制台作废并重新生成。

### 2.2 账号、密码、付款

- 不创建账号，不输入密码、验证码或支付信息。登录由用户自己完成。
- 遇到同意协议、开通服务、付款、充值、升级套餐的按钮：停在按钮前，说清"点下去会发生什么、花多少钱、能不能撤回"，由用户自己点。
- 看账单：请用户自己打开账单页，或者导出 PDF 给 AI 助手读。
- 有不需要新建账号、子账号或访问密钥的路线，就走那一条（例如在控制台里上传文件，再生成临时链接）。

### 2.3 下载

- 下载任何文件（音乐、音效、模型、素材）之前先问，说清文件名、来源网址、大小和许可证。
- 下载来的文件放进一个单独的新目录。用 Python 读它们时加 `-I`（隔离模式），免得目录里的同名文件被当成代码加载。
- 每个外部素材都记下来源、作者和许可证（见 `09-compliance.md`）。
- 时间紧时，先找电脑里已有的模型和素材，再考虑公共演示站或新下载。公共演示站常常排队或超时。

### 2.4 浏览器和外部平台

- 用户登录以后，AI 助手才在页面上操作；碰到 2.2 里的按钮就停。
- 上传之前，先确认会话能访问项目文件夹。文件超过网页上传上限（常见约 10 MB）时，降码率，不降分辨率。
- 不替用户对外发布、发消息或提交表单，除非用户在对话里明确要求了这一次。

### 2.5 对外公开的内容

- 投资人版或内部版可以讲内部结构。公开发布的物料（社交平台、公众号、公开演讲）不放爆炸图、透视图和能看出内部结构的镜头，也不写内部元件名称和工作原理。细节见 `09-compliance.md`。

## 3. 长任务

### 3.1 开跑前检查

- [ ] 电脑插上电源。
- [ ] 用户自己把系统睡眠设为"从不"。系统设置由用户改，AI 助手不改。
- [ ] AI 助手申请保持唤醒。它只在会话活跃时有效，所以上一条不能省。
- [ ] 工作流脚本放在项目文件夹里，每一步的结果写到磁盘上。
- [ ] 付费生成的"提交"和"查询"是两条命令，任务号写进日志。
- [ ] 接在长渲染后面的步骤（混音、编码）已经单独跑通过一次。
- [ ] 已经告诉用户完成时间。

> 案例：某产品片的笔记本夜里自己睡着了，后台渲染停了近 9 小时。从那以后，每个长任务开始前都先请用户插电、把睡眠设为"从不"。

### 3.2 能续跑

- 每一步的产出都写成文件。重启时看文件判断进度，跳过已完成的步骤，已经付过费的不再付。
- 工作流脚本放在项目的 `work/` 目录里，不要放在会话私有的目录里，那里重启后可能读不到。
- 中断以后，在脚本开头写一段续跑说明（"已完成：……；从……继续"），再重新启动。
- 账号额度用完、断网、会话结束，都会打断长任务。重启后马上给出新的完成时间。

### 3.3 提交和查询分开

- 付费生成拆成两条命令：`submit` 提交并把任务号写进日志；`poll` 按任务号查询状态、下载结果。
- 提交脚本在平台已经建好任务之后崩溃（断网时常见），就按日志里的任务号取回，不要重新提交。
- 遇到限流（HTTP 429）和网络错误自动重试，间隔逐次拉长。

### 3.4 本地渲染

- 3D 软件一次只开一个渲染进程。性能弱的电脑上并行启动会直接失败。要有日志、能续跑、失败自动重试（最多 3 次）。
- CPU 先让给"挡住下一步付费生成"的那个任务。
- 重渲之前，确认渲染程序实际从哪个文件读参数。输入一变，缓存必须失效，并提供强制重渲的选项。
- 规格或镜头表一变，马上停掉还在按旧数据跑的渲染。
- 长渲染放在后台，用监控工具看日志或文件修改时间，完成或出错时通知。

### 3.5 多个 agent 一起干活

- 两个 agent 不同时改同一个文件，第二个排队。
- 新反馈改变了刚启动的工作流的范围：停掉它，合并 brief，再重启。
- 不再需要的后台任务及时停掉，省额度也省电脑。
- 每个工作流都配一个独立的"挑刺"复审。复审必须看原始生成的片段，不能只看剪好的成片。

## 4. 电脑环境

### 4.1 通用

- Python 一律用 `uv run` 运行；脚本顶部用 PEP 723 内联元数据写明依赖。
- ffmpeg 用 `imageio-ffmpeg` 自带的那一份，不依赖系统里有没有装。
- 路径一律用 `pathlib` 拼，所有路径相对 `--project` 指定的项目根目录。
- 第一天就 `git init`，改代码前先提交一次。没有 git 时，改之前先复制备份（例如 `edit.py.bak-before-captions`）。
- 复杂改动写成文件再运行，不要在命令行里塞一大段代码（长 heredoc 容易被引号和反斜杠弄坏）。改完马上做语法检查，或用 `--dry` 试运行一次。
- 算术交给 Python，不靠 shell 里的计算器。
- 脚本生成的文件被人手改过，就在脚本旁注明"手改内容未合并，不要重跑"，直到改动搬回脚本里。
- 字幕要用中文字体时，确认系统里装了（例如 Noto Sans CJK、思源黑体），否则字会变成方块。

### 4.2 Windows

- 运行 Python 前设置 `PYTHONIOENCODING=utf-8`，否则打印中文路径时会报 UnicodeEncodeError。
- 传给 Python 的路径用 Windows 格式（`C:\...` 或 `C:/...`），不要用 Git Bash 的 `/c/...`。
- 读 Windows 程序写出的文本时，去掉行尾的 `\r`，否则逐行解析 JSON 会报错。
- 不要按进程名批量结束进程（可能被拒绝，也可能误杀用户自己的程序）；按进程号结束自己启动的那个。
- 防睡眠：请用户打开 设置 → 系统 → 电源（和电池）→ 屏幕和睡眠，把"接通电源时进入睡眠"设为"从不"。菜单名以系统版本为准。
- 并行启动多个 3D 渲染进程时，可能秒退并报 0xC0000142 之类的错误码，改成一次一个。

### 4.3 macOS

- `uv`、`imageio-ffmpeg` 用法相同，编码问题少见。
- 防睡眠：请用户在 系统设置 → 电池（或"节能"）里设为插电时不自动睡眠。长任务可以用 `caffeinate -dims <命令>` 包住，命令结束后自动恢复。
- 笔记本合盖会睡眠，除非接着电源和外接显示器。
- 文件名里有中文或空格时，命令行里要加引号。

### 4.4 Linux

- 防睡眠：用 `systemd-inhibit --what=sleep:idle <命令>` 包住长任务。
- 没有图形界面的机器上，3D 软件用无界面的后台模式渲染。
- 注意装中文字体。

## 5. 工具备注（有日期）

> 2026-10 在 Claude Code 桌面版上的记录。功能名称和限制会变，**以当前版本的文档为准**。
>
> 在 Codex 里使用时：skill 装在 `~/.agents/skills/`（或项目的 `.agents/skills/`），可以用 `$ai-product-video` 显式调用。下面这些能力（后台长任务、监控、浏览器操作、保持唤醒、多 agent 工作流）以 Codex 当前版本为准；没有对应能力时，改成分段运行，或者请用户手动执行那一步。

- 发文件到用户手机的上限约 30 MiB。
- "保持唤醒"只在会话活跃时生效；会话结束或电脑进入系统睡眠后，后台任务会停。
- 后台长任务可以交给监控类工具盯日志，完成或出错时通知。
- 浏览器扩展上传本地文件前，要先把项目文件夹加入会话可访问的目录。电脑操作类工具对浏览器常常只有只读权限，网页上的操作改用浏览器扩展。
- 多 agent 工作流很耗账号额度。会话额度或每周额度用完时，正在跑的工作流会中断，所以第 3.2 节的续跑设计是必需的。
- 3D 软件以 Blender 为例：无界面渲染用 `blender -b <文件> -P <脚本>`；在 Windows 上同时启动多个 Blender 进程，曾出现秒退并报 0xC0000142。
